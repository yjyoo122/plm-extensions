# I18N — Japanese / Korean UI Localisation (maintainer guide)

This document is for contributors and maintainers of `plm-extensions`. End users should read
[INSTALL-en.md](INSTALL-en.md) / [INSTALL-ja.md](INSTALL-ja.md) / [INSTALL-ko.md](INSTALL-ko.md) instead.

---

## 1. Why DOM-boundary translation, not source-level `t()`

The obvious way to localise an application is to wrap every user-visible literal in a translation
function — `t('Details')` — and never let an untranslated string reach the DOM.

That is the wrong choice for this repository, for three concrete reasons:

1. **Volume and shape of the call sites.** The browser code is ~2.5 MB across ~107 files, and it builds
   its DOM by string concatenation with jQuery:

   ```javascript
   elem.html('Details');
   $('<div></div>').attr('title', 'Clear selection of items');
   html += '<div class="button">Add Component</div>';
   ```

   There is no bundler, no build step, and no module system in the browser — scripts are plain
   `<script src>` includes. Introducing `t()` means editing thousands of individual expressions,
   many inside larger HTML string templates where the literal is not even a standalone token.

2. **Upstream mergeability.** This localisation layer is meant to stay mergeable with
   `dickmans/plm-extensions` upstream. A `t()` refactor touches essentially every application file and
   guarantees a conflict on every future upstream change. DOM-boundary translation touches a handful of
   framework files plus new files that upstream does not have, so upstream commits keep applying cleanly.

3. **Graceful degradation.** With `t()`, a missing key is a visible defect (`t()` returns the key, or
   worse, `undefined`). With DOM-boundary translation, an unknown string is simply left alone: the user
   sees the original English. Coverage can therefore grow incrementally, and a half-finished dictionary
   is still shippable.

**How it works.** `public/javascripts/framework/i18n.js` walks the DOM after load and observes further
changes with a `MutationObserver`. For each text node and for a fixed set of translatable attributes
(`title`, `placeholder`, `alt`, `aria-label`, `data-tooltip`, plus `value` on `input[type=button]` and
`input[type=submit]`), it trims the string and looks it up in
the active dictionary. On an exact whole-string hit, the text is replaced; on a miss, nothing happens and
the English stands. Matching is deliberately **exact and whole-string** — no substring or fuzzy matching —
because partial matching on PLM data would be far more destructive than a missing translation.

The trade-off this buys — and the price it charges — is section 6.

## 2. File map

| Path | Owner | Purpose |
| -- | -- | -- |
| `public/i18n/ja.json` | **you edit this** | Flat dictionary, `{ "English source": "日本語訳" }` |
| `public/i18n/ko.json` | **you edit this** | Flat dictionary, `{ "English source": "한국어 번역" }` |
| `public/i18n/dictionaries.js` | **generated — never hand-edit** | Sets `window.PLMX_I18N = { ja: {...}, ko: {...} }`. Produced by the build script from the two JSON files, so the browser loads one plain script instead of fetching JSON. |
| `public/javascripts/framework/i18n.js` | engine | Self-initialising runtime. Exposes `window.plmxI18n`. |
| `public/stylesheets/framework/i18n.css` | engine | Styling for the in-header language switcher. |
| `tools/i18n-extract.js` | CLI | Static scan of the source for candidate UI strings. |
| `tools/i18n-build.js` | CLI | Regenerates `dictionaries.js` from `ja.json` + `ko.json`. |

Both JSON files are **flat** — one level, no nesting, no namespaces. The key is the exact English string
as it appears in the DOM, after trimming leading/trailing whitespace. Keep the files sorted; it keeps
diffs readable and makes duplicate keys obvious.

```json
{
    "Add Component": "コンポーネントを追加",
    "Clear selection of items": "アイテムの選択を解除",
    "Details": "詳細"
}
```

After editing either JSON file you **must** regenerate the bundle:

```
node tools/i18n-build.js
```

Then hard-reload the browser (`Ctrl` + `F5`) — `dictionaries.js` is a static asset and will otherwise be
served from cache.

## 3. Workflow: growing the dictionary

The dictionary grows from what users actually see, not from a static scan. `tools/i18n-extract.js` gives
you a starting corpus, but it cannot know which literals ever reach the screen, and it misses strings
assembled at runtime. The runtime miss-log is the authoritative source.

1. **Start the server** and open the app you want to work on with the target language active, e.g.
   `http://localhost:8080/start?uilang=ja`.
2. **Use the app the way a user would.** Open dialogs, switch tabs, trigger error states, expand the BOM
   tree. Every string the engine looks up and fails to find is recorded in memory.
3. **Open the browser console** (`F12` → Console) and run:

   ```javascript
   plmxI18n.exportMissing()
   ```

   This downloads a JSON file containing every untranslated string collected in this session, already in
   dictionary shape with empty values:

   ```json
   {
       "Affected Items": "",
       "No records found": ""
   }
   ```

4. **Fill in the translations.** Use the terminology of the Japanese / Korean Fusion Manage UI, not a
   literal rendering: 部品表/BOM, 変更オーダ, ワークスペース, アイテム for Japanese; 부품표/BOM, 변경 오더,
   작업공간, 항목 for Korean. Where an Autodesk term is genuinely ambiguous, keep the English in
   parentheses after the translation — e.g. `"Descriptor": "記述子 (Descriptor)"`.
5. **Merge into the dictionary.** Paste the filled entries into `public/i18n/ja.json` or `ko.json`, keeping
   the file sorted. Do not replace the file with the export — the export only contains this session's
   misses.
6. **Rebuild and reload:**

   ```
   node tools/i18n-build.js
   ```

   Then `Ctrl` + `F5` in the browser and walk the same screens again to confirm.
7. Repeat per application. Working one application at a time keeps the terminology internally consistent.

### Measuring coverage

```javascript
plmxI18n.stats()
// { lang : 'ja', dictSize : 1150, translated : 214, missing : 37 }
```

| Field | Meaning |
| -- | -- |
| `lang` | The active language. `'en'` means the engine is idle and the other counters stay at zero. |
| `dictSize` | Number of entries in the active dictionary. |
| `translated` | Number of text nodes and attributes actually **replaced** so far. This counts replacements, not distinct strings — the same label rendered in twenty grid rows counts twenty times. |
| `missing` | Number of **distinct** strings that were looked up, not found, and judged collectable. |

There is no hit-rate field: `translated` and `missing` count different things and dividing one by the
other is meaningless. Use `missing` as the working number — it is exactly the size of the file
`exportMissing()` would hand you. For the strings themselves, with occurrence counts and a CSS path to
where each one was seen, use `plmxI18n.missing()` (most frequent first).

Both counters are per session and reset on reload, so measure after deliberately exercising the screens
you care about.

## 4. The false-positive problem

Because matching is whole-string and exact, the engine cannot tell a **UI label** from a **PLM data
value** that happens to be spelled the same way. If a user has an item whose Title is literally `New`,
and `"New"` is in the dictionary as `"新規"`, that item's title will be rendered as `新規` in every grid
that shows it. The data is not modified — this is display only — but it is still wrong and confusing.

Short labels are the risk: `New`, `Open`, `Draft`, `Released`, `Design`, `Assembly`, `Item`, `Change`.

Any element matching a skip selector is excluded from translation, together with all of its descendants.
The engine offers three ways to register one, plus an escape hatch to re-enable a nested region.

### Fix A — a skip selector in `settings/custom.js` (preferred, no code change)

```javascript
exports.i18n = {
    skipSelectors : ['#tableau-body td.table-field']
}
```

Restart the server for settings changes to take effect. The server hands this list to the page, which
publishes it as `window.PLMX_I18N_SKIP` **before** `i18n.js` runs; the engine reads that array during
initialisation.

> **Verify before relying on this.** The engine's only settings input is the global
> `window.PLMX_I18N_SKIP`. If your layout publishes the settings object under a different global name,
> `skipSelectors` is silently inert — the page loads, nothing is excluded, and there is no warning. Check
> `views/framework/layout.pug` and confirm that `window.PLMX_I18N_SKIP` is assigned from
> `exports.i18n.skipSelectors`. Until it is, use Fix B or Fix C.

### Fix B — `plmxI18n.addSkipSelector()` (works today, good for trying selectors out)

```javascript
plmxI18n.addSkipSelector('#tableau-body td.table-field');
plmxI18n.translateNow();   // re-run over the current page
```

Selectors added at runtime apply to everything translated from that point on. This is the fastest way to
find the right selector from the browser console before committing it to `settings/custom.js`.

### Fix C — a marker attribute or class on a container (for code you are writing anyway)

If you are already editing the code that builds a data region, mark the container. The engine honours
four equivalent markers on any ancestor:

```javascript
html += '<div class="values" data-i18n-skip>' + record.title + '</div>';
html += '<div class="values no-translate">'   + record.title + '</div>';
html += '<div class="values notranslate">'    + record.title + '</div>';
html += '<div class="values" translate="no">' + record.title + '</div>';
```

The opposite marker, `data-i18n-force`, re-enables translation inside an excluded subtree, so a whole
data panel can be skipped while its own toolbar keeps translating:

```javascript
html += '<div class="panel" data-i18n-skip>' +
            '<div class="panel-controls" data-i18n-force>' + buttons + '</div>' +
            rows +
        '</div>';
```

### Worked example — the Workspace Navigator grid

The Workspace Navigator (`public/javascripts/apps/navigator.js`, `views/apps/navigator.pug`) renders a
**transposed** grid inside `#tableau-table`: one row per field, one column per record.

| Region | Selector | Content | Translate? |
| -- | -- | -- | -- |
| Field labels, left-hand column | `#tableau-body td.first-col` | `tableauColumn.field.title` — comes from the tenant | No — out of scope, see section 5 |
| Record values | `#tableau-body td.table-field` | PLM data | **No — skip these** |
| Column headers (record descriptors) | `#tableau-header .table-column-descriptor` | PLM data | **No — skip these** |
| Toolbar, panel titles, dialogs | `#header-toolbar`, `.panel-controls`, … | hard-coded in this repository | Yes |

An item whose Descriptor is literally `New` appears both as a column header and, if it is also a field
value somewhere, inside a data cell — and with `"New": "新規"` in `ja.json` both come out as `新規`. So:

```javascript
exports.i18n = {
    skipSelectors : [
        '#tableau-body td.table-field',
        '#tableau-header .table-column-descriptor'
    ]
}
```

* Both data regions stop being translated, at every nesting depth below them.
* `Archive`, `Edit`, `Save Changes`, `Select Workspace`, `Filter`, `No data for this view` and the
  `title` tooltips in `.panel-controls` sit outside both selectors and keep translating.
* The left-hand field labels are untouched by these selectors, which is correct — they are tenant strings
  and should not be in the dictionary in the first place (section 5).

Result: labels localised, data verbatim. Choose the narrowest selector that covers the data region —
skipping a whole panel because of one cell throws away translation you already paid for.

### What *not* to do

Do not delete short strings like `"New"` from the dictionary to dodge the problem. That removes a
legitimate button label everywhere in order to fix one grid. Scope the exclusion, keep the translation.

## 5. Out of scope: PLM field labels

Field labels, picklist values, workspace names, workflow state names and tab titles that come from the
**tenant configuration** are delivered by the Fusion Manage REST API, not by this repository. Fusion
Manage localises them itself, based on the tenant configuration and the user's Autodesk language
preference.

Consequences:

* **Do not** add tenant field labels to `ja.json` / `ko.json`. If they are already localised by the
  tenant, adding them is dead weight; if they are not, the fix is in the tenant configuration, not here.
* A mixed-language screen (this layer's labels in Japanese, tenant fields in English) usually means the
  tenant's own localisation is incomplete. That is an administrator task in Fusion Manage.
* Values that *are* in scope: everything hard-coded in this repository's browser JS and Pug views.

## 6. Known limitations

Written honestly, so nobody rediscovers these the hard way.

* **Exact whole-string matching only.** `"Details"` translates; `"Details (3)"` does not, and neither does
  `"Item Details"` unless separately added. Strings assembled from fragments at runtime
  (`'Showing ' + n + ' of ' + total`) are effectively untranslatable in this design without splitting the
  fragments into their own dictionary entries, which reads badly in Japanese and Korean where word order
  differs. Some counters and status lines will stay English.
* **No plural rules, no gender, no interpolation.** There is no ICU message format. Japanese and Korean
  do not need plural agreement, which is why this is survivable, but it means English source strings that
  vary by count cannot be handled.
* **False positives on data values** — section 4. Mitigated, not eliminated. New applications and new
  tenant data can reintroduce it; the fix is per-region and manual.
* **Coverage is partial and always will be trailing.** Any upstream change that adds UI strings lands in
  English until someone runs `exportMissing()` again. This is by design — English fallback beats a broken
  screen — but it means the dictionary needs periodic maintenance after every upstream merge.
* **MutationObserver cost.** Translation runs on every DOM mutation batch. On very large BOM trees and
  long grids there is a measurable, though small, overhead. Mutations are debounced into one pass per
  animation frame, and a text node or attribute the engine has already written is not rewritten — but an
  inserted subtree *is* walked in full every time it is inserted, so a screen that re-renders tens of
  thousands of nodes will feel it. When that happens, the cheapest remedy is a skip selector over the
  data region (section 4), which removes it from the walk as well as from translation.
* **Text inside `<canvas>`, inside the Autodesk viewer (viewer3D), and inside cross-origin iframes is not
  reachable** by DOM traversal and is never translated.
* **`document.title` is translated once**, during the initial sweep at `DOMContentLoaded`. A title
  assigned later by application code is not observed and stays in English. Browser-native UI (`alert()`,
  `confirm()`, file pickers, print dialogs) is outside the DOM boundary altogether and always stays in
  English / the OS language.
* **Server-side strings** — HTTP error pages, console log output, and anything rendered by Pug before the
  engine initialises — flash in English briefly or stay English. Pug-rendered page content is translated
  on the first pass, so a very brief flash of English is possible on slow machines.
* **Reversibility.** The engine never stores the original string for text nodes it has replaced, so
  switching language mid-page triggers a full reload rather than an in-place retranslation. This is
  intentional: retranslating already-translated text would compound errors.
